# Правила отладки Chimp (EL2-гипервизор + FreeBSD-гость на живом железе)

Выведены из разбора «в чём сложность» (2026-07-15). Не абстрактные принципы —
каждое правило отвечает на конкретный способ, которым эта задача обманывает.
Работать строго по ним.

---

## R1. Снимок ≠ живость. Никогда не объявляй «завис» по одному `gr`.
`gr`/`gva`/breadcrumb дают **состояние**, а не **время**. «Жив и крутит poll-петлю»
и «мёртв» дают побитово одинаковый снимок.

**Прежде чем сказать «hang», предъяви меру прогресса во времени:**
- читается ли буфер вывода (консоль vconsole — идут ли новые байты);
- перешагнул ли гость дальше — `onebp` на *более позднем* boot-этапе срабатывает;
- меняются ли SP / ELR / цепочка вызовов между тиками (снять дважды с паузой).

Пока такой меры нет — формулировка только «последний пойманный фрейм — X»,
без вывода о том, жив он или нет.

## R2. Читай точный matching-исходник ПЕРЕД тем, как строить теорию.
Симптом бывает снят точно, но недоопределён — совместим с веером причин
(урок off-by-one MODINFOMD: `x21==howto_val` был верен, теория «компилятор
вернул HOWTO как lastaddr» — нет; правда — теги 7/8/9 вместо 6/7/8).

- Сверяйся с **точным commit'ом**, из которого собран бинарь на плате
  (сейчас: `freebsd-src` releng/15.1 @ `9263fb9`, версия
  `releng/15.1-9263fb9bab26-dirty`). Не с main, не «примерно».
- Проверка гипотезы на железе дороже чтения кода (см. R4) → чтение спеки/исходника
  по умолчанию раньше, чем прошивка.

## R3. Симптом может быть артефактом моего собственного механизма. Снимай слои.
Мои же механизмы искажают картину: TVM/vbar-override, unmap вектора для
first-fault, trap-and-emulate в vconsole. Фолт на UART0 MMIO вполне может быть
**поведением vconsole**, а не багом гостя.

- Когда наблюдение могло быть создано моим инструментом — сделай A/B, отключив
  ровно один механизм (пример: `-DDBG_NO_TVM` доказал, что TVM ни при чём —
  фолт идентичен, т.к. stage-2 abort'ы летят в EL2 by design).
- Один эксперимент = один отключённый/изменённый механизм. Иначе результат
  неинтерпретируем.

## R4. Итерация на железе дорогая — экономь циклы платы.
Плата без software-reset (заметка Chimp M64: reboot/reset вешает борт;
`bootdelay=-1`). Один цикл = ручной power/ловля U-Boot + прошивка + переподключение.

- Меняй **одну переменную за цикл платы**. Никогда не смешивай несколько правок
  «заодно» — при неожиданном результате не разделишь причины.
- Перед прошивкой выпиши ожидаемый результат для обеих веток (что увижу, если
  гипотеза верна / неверна). Если снимок не различает ветки — эксперимент
  бессмысленный, не жги цикл.
- Батчируй пассивные наблюдения (несколько `gr`/`gva`/breadcrumb) в один заход,
  раз уж плата уже загружена.

## R5. Отладочный канал — единственная точка отказа. Береги видимость.
EMAC/USB-gadget-консоль живёт *внутри* системы под тестом. Когда «залип гость»,
сначала исключи, что залип сам транспорт наблюдения.

- Не трогай EMAC/USB-gadget/vconsole той же правкой, что и логику гостя.
- Долгосрочно: независимый UART debug-header и/или внешний хаб с
  переключаемым питанием как страховка от single-point-of-failure.

## R6. Гигиена окружения (проверено, повторяется).
- **Прокси:** `http_proxy`/`https_proxy` ломают localhost/LAN и даже git к github.
  Для любого fetch/probe локального/LAN/git — `env -u http_proxy -u https_proxy …`
  или `curl --noproxy '*'`.
- **`cp` с алиасом `-i`** молча пропускает overwrite в неинтерактиве → `\cp -f`.
- **make не видит смену `CFLAGS`** между запусками → `rm -f` затронутых `.o`
  перед пересборкой с новым флагом (напр. `-DDBG_NO_TVM`).

## R7. Фиксируй понимание сразу — и корректируй, когда оно оказалось ложным.
Симптом описывай как факт, объяснение — как гипотезу с её статусом
(предположение / проверено / опровергнуто). Когда теория опровергнута —
переписывай комментарий/PROGRESS.md, а не оставляй красивое-но-ложное объяснение
(как было со снятым «двумя quirks» блоком в kload.c).

---

### Чек-лист перед следующим циклом платы
1. Какую **одну** переменную меняю?
2. Прочитал ли точный matching-исходник по этому месту (R2)?
3. Различает ли мой снимок обе ветки исхода (R4)?
4. Не артефакт ли это моего механизма — нужен ли A/B (R3)?
5. Есть ли мера живости, если вопрос про «завис/жив» (R1)?
