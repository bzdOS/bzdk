### 4.4 Interrupt Parent / Cells Handling

FreeBSD's OFW interrupt parsing (via `intr_pic_register` at line 1155) walks the `interrupt-parent` phandle chain and uses the parent's `#interrupt-cells` to decode the child's `interrupts` property.

**Critical Mismatch:**
- `pinctrl@1f02c00` has `#interrupt-cells = <0x03>` (it *is* an interrupt controller for its GPIO lines)
- Its `interrupt-parent` is `r_intc` which has `#interrupt-cells = <0x02>`
- The `interrupts` property in `pinctrl@1f02c00` has **3 cells** (`<0x00 0x2d 0x04>`)
- But `r_intc` expects **2 cells** per interrupt specifier

When FreeBSD's OFW interrupt code tries to decode the `interrupts` property of `pinctrl@1f02c00`, it will:
1. Follow `interrupt-parent` to `r_intc` (phandle 0x4e)
2. Read `r_intc`'s `#interrupt-cells` = 2
3. Try to parse the 3-cell `interrupts` property as a sequence of 2-cell specifiers
4. **Fail** — 3 is not a multiple of 2

This is a known DT encoding error: a node's `interrupts` property must have a cell count that is a multiple of its **parent's** `#interrupt-cells`, not its own.

## 5. Predicted Observable Behaviour

### What "cannot allocate device resources" Means

In `aw_gpio_attach` (line 1103–1106):
```c
if (bus_alloc_resources(dev, aw_gpio_res_spec, sc->sc_res) != 0) {
    device_printf(dev, "cannot allocate device resources\n");
    return (ENXIO);
}
```
This message is printed when **either** MEM or IRQ allocation fails.

### Why It Fails Here

1. **MEM allocation** — Should succeed. `reg = <0x1f02c00 0x400>` is valid, identity-mapped via `soc/ranges;`.

2. **IRQ allocation** — **Will fail** because:
   - The OFW interrupt parser cannot decode the `interrupts` property due to the `#interrupt-cells` mismatch (3 cells provided, parent expects 2)
   - `bus_alloc_resources` for `SYS_RES_IRQ` returns failure
   - The driver prints "cannot allocate device resources" and returns `ENXIO`

### Evidence from Code Path

The exact error message `"cannot allocate device resources"` appears **only once** in `aw_gpio.c` (line 1104), inside the `bus_alloc_resources` failure block. Since MEM allocation is straightforward, the IRQ allocation is the failing half.

## 6. Root Cause Summary

| Item | DTB Value | Expected by Parent (`r_intc`) |
|------|-----------|-------------------------------|
| `pinctrl@1f02c00` `interrupts` | 3 cells (`0x00 0x2d 0x04`) | 2 cells per specifier |
| `r_intc` `#interrupt-cells` | N/A | **2** |
| `pinctrl@1f02c00` `#interrupt-cells` | **3** (for *its* children) | N/A |

**The bug:** The `pinctrl@1f02c00` node declares `#interrupt-cells = <3>` for its *own* role as an interrupt controller (for GPIO interrupts), but its `interrupts` property (describing *its* interrupt to the parent) must conform to the **parent's** `#interrupt-cells` (which is 2). The DTB incorrectly uses 3 cells.

### Correct Encoding for `r_intc` Parent

For `allwinner,sun6i-a64-r-intc` (`#interrupt-cells = 2`), each interrupt specifier is:
```
<type irq>
```
Where `type` = 0 for SPI, `irq` = SPI number (0–1019).

The current `interrupts = <0x00 0x2d 0x04>` appears to encode:
- `0x00` = type (SPI)
- `0x2d` = SPI 45
- `0x04` = trigger flags (level-high) — **this third cell is wrong for a 2-cell parent**

The trigger flags belong in the *child's* `#interrupt-cells` (3 cells: `<type irq trigger>`), not in the parent's encoding.

---

## 7. Fix Required

The `pinctrl@1f02c00` node's `interrupts` property must be **2 cells** to match `r_intc`'s `#interrupt-cells = 2`:

```dts
interrupts = <0x00 0x2d>;  /* type=SPI, irq=45 */
```

The trigger configuration (level-high) is handled by the GPIO interrupt controller *internally* (via its own `#interrupt-cells = 3` when children request GPIO interrupts), not in the connection to the parent interrupt controller.
